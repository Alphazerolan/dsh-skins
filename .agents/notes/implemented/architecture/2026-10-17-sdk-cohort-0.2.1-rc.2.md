# Agent Note: The plugin cohort advances to 0.2.1-rc.2

Status: implemented

## Problem

The repository tracked the 0.1.7-rc.1 SDK cohort while the approved host
cohort moved on. The family first approved 0.2.1-alpha.5 (installed on this
branch, 8e6fe47), then approved 0.2.1-rc.2 as the cohort target — the
published `alpha` line stops at 0.2.1-alpha.5 and `next` serves 0.2.1-rc.2.
Staying on either older literal leaves the declared host floor
(`dsh.engines.dsh`, the `@deepseek-ai/dsh` peer, the README badge), every
consumed `@deepseek-ai/*` specifier, and the release-age ledger in
`pnpm-workspace.yaml` trailing the cohort the family ships against.

## Decision

**Every consumed `@deepseek-ai/*` specifier, the host floor, the vendor
pins, and the release-age ledger name 0.2.1-rc.2; the cohort is installed
exactly as published.**

- `package.json` — `dsh.engines.dsh` and the `@deepseek-ai/dsh` peer floor
  move to `>=0.2.1-rc.2`. The nine consumed SDK devDependencies are pinned
  EXACT (`0.2.1-rc.2`, no caret): a caret prerelease range would float to
  whatever `next` serves next, and the freeze names the approved cohort.
  The vendor pins move with the cohort's now-stable companions:
  `@deepseek-ai/cordis` `^4.0.4` -> `^4.0.5` (4.0.5 stable replaced the
  cohort's 4.0.5-alpha.2), `@deepseek-ai/schemastery` `^3.18.4` ->
  `^3.18.5`; `@deepseek-ai/cosmokit` stays transitive and resolves 1.8.6
  stable.
- `pnpm-workspace.yaml` — `minimumReleaseAgeExclude` is regenerated from
  the rebuilt lockfile: one entry per resolved package version, so the
  ledger matches exactly what a fresh install resolves. Packages the
  cohort no longer publishes stay out (dsh-invariants ended at 0.2.0-rc.2;
  @mlgbnb/dsh-archive-manager is no longer pulled).
- `contracts/official-tokens-v1.json` — rescanned against the published
  0.2.1-rc.2 surfaces (dsh-client-ui-theme lib + dsh-web-frontend
  dist/assets). The token set is UNCHANGED from the 0.2.1-alpha.5 contract
  (0 added, 0 removed); only the `source` field names rc.2. The rc.2 shell
  index bundle is byte-identical to alpha.5's, which is why.
- `shared/web-platform.ts` — unchanged at this advance: the rc.2
  staticModules table was re-verified against the published shell bundle
  and remains the same 11 rows confirmed at alpha.5 (react,
  react/jsx-runtime, react-dom, react-dom/client, cordis, zod,
  @tanstack/react-virtual, dsh-client-store, dsh-client-ui-slots,
  dsh-client-ui-primitives, dsh-client-ui-dockkit).
- The client inject contract needed no edit at either advance: all five
  `dsh.client.inject` names are browser-roster rows of dsh-web-app's
  cordis.patch.yml at the pinned cohort (api-remotes, ui-theme, locale,
  ui-renderer, ui-settings), and the four runtime services they back
  (`slots`, `locale`, `theme`, `configForms`) match the providers' service
  names in the installed packages.
- The one source adaptation came at the alpha.5 advance: 0.2.1 removed the
  `mode` field from `ConfigFormSnapshot`, and the section projection, the
  unavailable snapshot, one diagnostic string and the test stubs stopped
  carrying it. rc.2 changed nothing further in the consumed surface.

## Alternatives considered

- **Caret devDependencies with a frozen lockfile.** Rejected at the
  alpha.5 advance and again here: any fresh `pnpm install` resolves
  whatever `next` serves, which is by definition not the approved cohort.
  The exact pin is the freeze.
- **Leaving the vendor pins on 4.0.4 / 3.18.4.** Rejected: the cohort
  ships cordis 4.0.5 and schemastery 3.18.5 as stable now, so the
  repository's direct ranges move with them instead of carrying a second,
  older copy of each through the tree.
- **Keeping the alpha.5 ledger entries.** Rejected: the ledger must match
  what a fresh install actually resolves; stale exclusions hide drift.
- **Re-running the token snapshot from a stale install.** Rejected: the
  `source` field must name what was scanned; the rc.2 scan ran against the
  published rc.2 tarballs.

## Consequences

`pnpm install --prefer-offline`, `pnpm typecheck`, `pnpm test` (710 tests),
`pnpm build`, `pnpm skin-center:check` (61 catalog skins) and
`pnpm skin-hooks:check` pass on the rc.2 cohort, and the committed `lib/`
matches the rebuilt sources. The ignored-builds notice of pnpm 11
(node-pty, koffi, protobufjs, @google/genai, dsh-subprocess-local) predates
the cohort work — the same packages were ignored on the 0.1.7 lockfile —
so script runs need `--config.verify-deps-before-run=false` locally, the
lane CI covers with `--ignore-scripts`.

Upstream publish timing is a real hazard on same-day cohorts: the first
rc.2 install failed on `@deepseek-ai/dsh-client-ui-settings-account` —
dsh-web-app@0.2.1-rc.2 pins it exact while its npm publish landed minutes
later (the rest of the 131 rc.2-pinned packages were already present). A
missing-publish failure on a fresh cohort is a wait-and-retry, not a
repository defect; do not patch around it. The wallpaper / renderer domain
was not touched at either advance. The next cohort move repeats this
recipe: exact pins, vendor pins alongside, lockfile-regenerated ledger,
module-table and token-contract rescan against the published tarballs.
