# Agent Note: The plugin cohort advances to 0.2.1-alpha.5

Status: implemented

## Problem

The repository tracked the 0.1.7-rc.1 SDK cohort while the approved host
cohort moved on: 0.2.1-alpha.5 is the target this package must build, test
and declare against, and npm `next` already serves 0.2.1-rc.1, which the
upgrade does NOT approve. Staying on 0.1.7-rc.1 leaves the declared host
floor (`dsh.engines.dsh`, the `@deepseek-ai/dsh` peer, the README badge) and
every consumed `@deepseek-ai/*` specifier trailing the cohort the family
ships against, and the release-age ledger in `pnpm-workspace.yaml` describing
packages the cohort no longer publishes.

## Decision

**Every consumed `@deepseek-ai/*` specifier, the host floor, and the
release-age ledger now name 0.2.1-alpha.5 exactly; the npm `next` line
(0.2.1-rc.1) is never followed.**

- `package.json` — `dsh.engines.dsh` and the `@deepseek-ai/dsh` peer floor
  move to `>=0.2.1-alpha.5`. The nine consumed SDK devDependencies are pinned
  EXACT (`0.2.1-alpha.5`, no caret): a caret prerelease range would resolve
  the unapproved 0.2.1-rc.1 that npm `next` already serves. This follows the
  family pattern of caret devDependencies only while the pinned version is
  also the newest; the freeze makes the exactness explicit.
- `pnpm-workspace.yaml` — `minimumReleaseAgeExclude` is regenerated from the
  rebuilt lockfile: one entry per resolved package version, so the ledger
  matches exactly what a fresh install resolves. Packages the cohort no
  longer publishes drop out (dsh-invariants last saw 0.2.0-rc.2;
  @mlgbnb/dsh-archive-manager is no longer pulled), alongside every stale
  0.1.7-alpha.2 union entry. New cohort companions enter (node-addon-system
  0.1.2, libreoffice-kit 0.1.5, cordis 4.0.5-alpha.2 beside the devDep's
  4.0.4, cosmokit 1.8.6-alpha.2 beside 1.8.5, schemastery 3.18.5-alpha.2
  beside 3.18.4, and the cordis-plugin 1.x alphas).
- `contracts/official-tokens-v1.json` and
  `src/core/css-safety/official-tokens.generated.ts` — regenerated from the
  published 0.2.1-alpha.5 surfaces (dsh-client-ui-theme lib +
  dsh-web-frontend dist/assets, scanned by the family script
  `scripts/official-tokens-snapshot.mjs`). 30 tokens join, none leave; the
  contract stays a superset, so no installed skin's token use changes
  meaning.
- `shared/web-platform.ts` — the platform seed gains `zod` and
  `@tanstack/react-virtual`: the frozen module table in the 0.2.1-alpha.5
  shell bundle adds both rows (verified in the published
  dsh-web-frontend dist; the 0.2.0-rc.2 table did not have them).
- The one source adaptation: 0.2.1-alpha.5 removed the `mode` field from
  `ConfigFormSnapshot` (the `'host' | 'memory'` sync indicator is gone —
  status `unavailable` now covers the process-local case). The section
  projection, the unavailable snapshot, one diagnostic string, and the test
  stubs stop carrying the field. No behavior changes: nothing branched on
  `mode`.
- The client inject contract needs no edit: all five `dsh.client.inject`
  names are browser-roster rows of dsh-web-app@0.2.1-alpha.5's
  cordis.patch.yml (api-remotes, ui-theme, locale, ui-renderer, ui-settings),
  and the four runtime services they back (`slots`, `locale`, `theme`,
  `configForms`) still match the providers' service names in the installed
  0.2.1-alpha.5 packages.

## Alternatives considered

- **Caret devDependencies (`^0.2.1-alpha.5`) with a frozen lockfile.**
  Rejected: any fresh `pnpm install` (new clone, CI without
  `--frozen-lockfile`, the pnpm run deps-check) resolves the unapproved
  0.2.1-rc.1 from npm `next`. The exact pin is the freeze.
- **Keeping the old ledger entries "just in case".** Rejected: the skill
  rule is to reconcile the ledger with the approved exact versions —
  stale exclusions hide what a fresh install actually resolves, and the
  0.1.7-era unions double every row.
- **Declaring the floor at `>=0.2.1-rc.1` to match `next`.** Rejected: the
  approved cohort is 0.2.1-alpha.5; the floor names the cohort being
  installed, never a newer one (the floor is a minimum, so a hypothetical
  newer host still satisfies it — but the repository declares what it
  validated).
- **Regenerating the token contract against the local 0.1.7 install or
  skipping regeneration.** Rejected: the `source` field must name what was
  scanned; a contract that claims 0.1.7-rc.1 surfaces while the package
  declares a 0.2.1-alpha.5 floor is a false statement the skin gate trusts.

## Consequences

`pnpm install --prefer-offline`, `pnpm typecheck`, `pnpm test` (710 tests),
`pnpm build`, `pnpm skin-center:check` (61 catalog skins) and
`pnpm skin-hooks:check` pass on the new cohort, and the committed `lib/`
matches the rebuilt sources. The ignored-builds notice of pnpm 11
(node-pty, koffi, protobufjs, @google/genai, dsh-subprocess-local) predates
this change — the same packages were ignored on the old lockfile — so
script runs need `--config.verify-deps-before-run=false` locally, the same
lane CI covers with `--ignore-scripts`.

The wallpaper / renderer domain was not touched: no file under
`src/client/runtime/`, `src/core/wallpaper-handoff.ts` or a skin stylesheet
carries a cohort edit. The next cohort advance repeats this recipe: exact
pins, lockfile-regenerated ledger, regenerated token contract, module-table
diff against the published shell bundle.
